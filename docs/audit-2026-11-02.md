# November 2 review

Reviewed the current application, prior audits, weather and persistence boundaries, navigation, accessibility ownership, PWA installation and updates, notification operations, loading assets, and test selection. The baseline revision `2c2cd4a` passed its [complete release CI](https://github.com/TGthms/duskline/actions/runs/40277209745). Fresh syntax/content checks also passed. Weather edge cases were reproduced with isolated provider fixtures; they are not measurements of live provider accuracy.

## Interaction follow-up

- Phone forecast charts activate after a 160ms stationary touch. Once active, the cursor follows the finger. Release or cancellation restores today's current model hour or a future day's range. A swipe before activation remains a scroll gesture. Explicit hour entry and keyboard exploration remain supported. Offset-bearing timestamps use their actual instant for current-hour selection.
- On portrait phones, Map shares the application header and bottom navigation. Map has a selected tab state and region semantics. Settings, nested notification preferences, city detail returns, Back, rapid tab switches and responsive presentation preserve their owning context. Desktop and short landscape screens retain the dialog presentation.
- Installed windows suppress browser page pinch scaling while retaining scrolling and the map renderer's own two-finger zoom. Regular browser pages retain pinch zoom. This limits pinch-based text magnification inside installed windows; operating-system magnification is separate.

The runtime shell is v100; the locale cache stays v85. Existing translated labels cover these interactions. No language packs, notification backend or dependencies change.

## Confirmed remaining bugs

1. **Hourly-strip boundary:** at exactly 22:00, the strip can include the 21:00 sample because the lower bound includes a reading exactly one hour old. Detail calls the first sample “Now.” Use one shared hourly interval policy for the strips and add exact-boundary coverage. The chart's current-point correction above addresses a separate timestamp selection path.
2. **Saved-place acknowledgement:** when the favorites write throws `QuotaExceededError`, the app still announces “Added to My Sky” while the favorite remains absent. Persistence should return an explicit outcome; preserve usable session state and describe storage failure honestly. Apply the policy consistently to add, remove, reorder and Undo.
3. **Shared-link recovery:** if the requested city's forecast fails while featured-city requests succeed, the app silently displays Horizon with no city-specific failure or Retry. Keep the requested city visible in a recoverable error state, including when opened from a notification.

These remain findings for a separate fix batch.

## Recommended priorities

1. **Gate the primary host on release checks.** The baseline Cloudflare check completed before its release CI. The GitHub Pages workflow already waits for CI. Make Cloudflare publish the validated revision as well, with an exercised rollback and a post-deploy shell/API smoke check. Cloudflare supports [production deployment controls](https://developers.cloudflare.com/pages/configuration/branch-build-controls/); dashboard configuration was not changed in this review.
2. **Simplify the personal forecast model.** Present one primary place and one saved-place collection consistently. The primary picker still explains its purpose as choosing the greeting's location, although it controls the whole dashboard and notification following. Align the copy and management flows with that actual behavior.
3. **Make the first screen forecast-led.** A persistent Install action and full search field compete with the primary forecast on browser phones. Consider dismissible installation guidance, a compact place/search entry and a clearer daily summary. Review a prototype before changing the hierarchy. Keep home useful for a quick check and detail useful for deeper exploration, with fewer repeated sections and transitions.
4. **Complete physical-device acceptance.** Exercise installed iOS cold launch, VoiceOver, enlarged text, the software keyboard, safe areas, background/resume, rotation, offline relaunch, update acceptance and actual push receipt. Include an older iPhone and Android Chrome. Browser and input-protocol checks do not establish these device results.
5. **Make data ownership visible.** Add a compact data/support entry with app version, offline forecast availability and an explicit recovery path. An export/import of saved places and preferences would help device changes without requiring accounts. A reset must reconcile notification disable intent before discarding its ownership record.
6. **Observe production failures.** Worker aggregate logs exist, but frontend recovery mostly has console-level evidence. Add a user-initiated diagnostic copy action with release/browser/error codes, and narrowly scoped health checks for forecast fetches, CAP, updates and push poll age. Keep coordinates, push endpoints, capability tokens and private keys out of diagnostics.
7. **Profile before optimizing startup.** The baseline entry page references 33 scripts and 15 stylesheets: approximately 1.06 MB raw, or 277 kB when each is gzip-compressed, excluding fonts and lazy map assets. This is an asset inventory, not a measured transfer or slowness claim. Measure time to a usable personal forecast and response latency on a slower phone before deciding what to defer or combine. The main coordinator is about 5,750 lines; the largest weather stylesheet about 4,680. Extract cohesive ownership and consolidate overlapping rules when changing those areas.
8. **Review localization in use.** Automated key and placeholder parity cannot establish natural wording or useful number/date presentation. Review representative long-label, CJK and RTL languages with speakers, including notification permission/recovery and the primary-place terminology.

Before wider distribution, record provider request budgets and notification capacity under actual usage. Open-Meteo's [free plan](https://open-meteo.com/en/pricing) has non-commercial usage limits and no uptime guarantee. Batched locations and selected variables affect usage accounting. There is no evidence here that the current installation has exceeded a provider limit.

A useful later feature would be a small, deterministic planning summary for a chosen time window: rain risk, temperature change and wind. Validate whether users want commute or outdoor planning before introducing more settings or notification categories.
